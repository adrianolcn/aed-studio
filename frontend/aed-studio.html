// 01 · a pergunta mais fundamental
ponto de partida
Antes de qualquer estrutura de dados, antes de qualquer análise de complexidade, existe uma pergunta que precisa ser respondida: o que estamos projetando, afinal? A resposta é: um algoritmo. Toda esta plataforma — BSTs, heaps, grafos, paradigmas — é sobre como projetar, analisar e implementar algoritmos corretamente e de forma eficiente. Nada faz sentido sem esse ponto de partida.
Analogia: um músico pode saber teoria harmônica avançada, contraponto e orquestração. Mas se nunca parou para entender o que é som — uma oscilação de pressão no ar com frequência e amplitude —, toda aquela teoria paira no vazio. Algoritmos são para esta plataforma o que o som é para a música: a matéria-prima fundamental.
// 01.1 · algoritmo não é só receita
o que diferencia um algoritmo de uma instrução comum?
É comum dizer que algoritmo é uma "receita". A comparação ajuda, mas também pode enganar. Uma receita de bolo aceita improvisos: "asse até dourar", "adicione sal a gosto", "misture bem". Um algoritmo, em ciência da computação, precisa ser mais rigoroso: cada passo deve ser executável, a entrada precisa estar clara, a saída esperada precisa ser definida e deve haver um critério para dizer se o resultado está correto.
Cartões comparativos: leia lado a lado, não como etapas
Receita humana: tolera interpretação, contexto e experiência. Duas pessoas podem executar de modos ligeiramente diferentes e ainda chegar a algo aceitável.
Algoritmo computacional: exige precisão. Se duas execuções com a mesma entrada produzem resultados incompatíveis sem motivo previsto, há um problema de especificação.
Heurística: busca uma solução boa quando a ótima é cara demais. É útil, mas nem sempre garante a melhor resposta.
Programa: é uma implementação concreta de um ou mais algoritmos, escrita em uma linguagem, rodando sobre dados reais e limitações reais de máquina.
Exemplo de escolha: para procurar um nome numa lista pequena, uma busca linear é simples e suficiente. Para procurar em milhões de registros ordenados, busca binária faz muito mais sentido. Para procurar por uma chave em um sistema que muda o tempo todo, uma tabela hash pode ser melhor. A pergunta não é "qual algoritmo é o melhor?", mas "melhor para quais dados, restrições e operações?".
// 02 · origem do nome — al-Khwārizmī
SÉCULO IX — BAGDÁ
O matemático persa Muḥammad ibn Mūsā al-Khwārizmī (c. 780–850 d.C.) escreveu o tratado Kitāb al-mukhtaṣar fī ḥisāb al-jabr wa-l-muqābala — que deu origem à palavra álgebra — e um manual de aritmética cujo título latino começava com "Dixit Algorizmi..." (Disse al-Khwārizmī...). A latinização do seu nome, Algorismus, virou sinônimo de "procedimento de cálculo passo a passo" e, séculos depois, algorithm.
MAS O CONCEITO É MAIS ANTIGO
O Algoritmo de Euclides para o MDC (c. 300 a.C.) é um dos primeiros algoritmos documentados da história — mais de mil anos antes de al-Khwārizmī. O Crivo de Eratóstenes (c. 240 a.C.) para encontrar números primos é outro. A ideia de um procedimento finito e sistemático precede o nome que a descreve.

// 03 · definições — das mais simples às mais formais
Cada definição abaixo acrescenta uma camada de rigor à anterior. Lê-las em sequência revela por que a definição informal "um conjunto de passos para resolver um problema" é insuficiente para o trabalho científico — mas é por onde todo mundo começa.
01 definição informal
Um algoritmo é uma sequência finita de passos bem-definidos para resolver um problema ou realizar uma tarefa.
É o ponto de partida didático. Basta para explicar a uma criança como amarrar o tênis. Não basta para provar que um programa está correto, porque não especifica o que significa "bem-definido", nem quem ou o quê executa os passos.
02 Cormen et al. — CLRS, 4ª ed. (2022)
"Um algoritmo é qualquer procedimento computacional bem-definido que toma algum valor, ou conjunto de valores, como entrada (input) e produz algum valor, ou conjunto de valores, como saída (output) em um tempo finito. Um algoritmo é, portanto, uma sequência de passos computacionais que transformam a entrada em saída."
O avanço sobre a definição informal: entrada → saída torna o algoritmo uma função no sentido matemático. "Tempo finito" exclui loops infinitos. "Procedimento computacional bem-definido" ainda deixa implícito o modelo de computação, mas é operacionalmente suficiente para o estudo de algoritmos.
Ref: Cormen, T. H., Leiserson, C. E., Rivest, R. L., Stein, C. Introduction to Algorithms, 4ª ed. MIT Press, 2022. Cap. 1, p. 5.
03 Knuth — TAOCP, vol. 1 (1968/1997)
Knuth define um algoritmo por cinco propriedades que todo procedimento deve ter para ser considerado um algoritmo válido:
FINITUDE
Sempre termina após um número finito de passos
DEFINIÇÃO
Cada passo é precisamente e sem ambiguidade definido
ENTRADA
Zero ou mais quantidades fornecidas antes de iniciar
SAÍDA
Uma ou mais quantidades produzidas ao final
EFETIVIDADE
Cada operação é suficientemente básica para ser executável
O avanço: Knuth separa efetividade de definição. Um passo pode ser matematicamente bem-definido mas não efetivo — por exemplo, "encontre o décimo dígito de π tal que a soma dos seguintes 1000 dígitos seja primo" é definido mas pode não ser computável em tempo finito. A finitude distingue algoritmo de método computacional (que pode não terminar).
Ref: Knuth, D. E. The Art of Computer Programming, vol. 1, 3ª ed. Addison-Wesley, 1997. Sec. 1.1, p. 4-6.
04 Turing (1936) — a fundação matemática
Alan Turing, em On Computable Numbers, with an Application to the Entscheidungsproblem (1936), formalizou o que significa "computar" através da Máquina de Turing: um dispositivo abstrato com uma fita infinita, uma cabeça de leitura/escrita e uma tabela de transições de estados. Um algoritmo, nessa visão, é qualquer procedimento que uma Máquina de Turing pode executar.
TESE DE CHURCH-TURING
Qualquer função que pode ser calculada por um procedimento efetivo pode ser calculada por uma Máquina de Turing. Isso equivale a dizer: algoritmo = o que uma Máquina de Turing pode fazer. Essa é a definição mais formal e matematicamente sólida que temos — e é ela que permite provar que certos problemas são não-computáveis (como o Problema da Parada).
O avanço: a Máquina de Turing fornece um modelo de computação concreto. Toda a teoria da complexidade (P, NP, NP-completo) é construída sobre esse alicerce. Quando Cormen diz "procedimento computacional bem-definido", ele está implicitamente assumindo esse modelo.
Ref: Turing, A. M. "On Computable Numbers, with an Application to the Entscheidungsproblem." Proceedings of the London Mathematical Society, ser. 2, vol. 42, 1936.
05 definição operacional (síntese para este curso)
Um algoritmo é um procedimento finito, determinístico, correto e analisável que transforma uma instância de um problema (entrada) em sua solução (saída), consumindo recursos computacionais mensuráveis — tempo e espaço.
Finitotermina para toda entrada válida (Knuth).
Determinísticomesmo resultado para mesma entrada, exceto algoritmos randomizados tratados à parte.
Corretoproduz a saída esperada para toda entrada válida; exige prova de correção, não só testes.
Analisávelpermite quantificar recursos por notação assintótica, como tempo e espaço.
// 04 · a relação indissociável: algoritmos ↔ estruturas de dados
por que uma coisa não existe sem a outra
Niklaus Wirth — criador das linguagens Pascal e Modula-2 — intitulou seu livro fundamental de 1976 com precisão cirúrgica: Algorithms + Data Structures = Programs. A equação não é metáfora: um algoritmo que não tem onde armazenar e organizar os dados que manipula não pode ser implementado. E uma estrutura de dados sem os algoritmos que a operam é apenas memória inerte.
ALGORITMO
Define o que fazer — a lógica de transformação. Busca binária, Merge Sort, BFS. Sem dados para operar, é apenas uma descrição abstrata.
⇄
ESTRUTURA DE DADOS
Define como organizar os dados — layout, acesso, custo. Array, Heap, BST, Grafo. Sem algoritmos, é apenas ocupação de memória.
Exemplo concreto: Dijkstra (algoritmo) de caminhos mínimos é O((V + E) log V) porque usa um heap de mínimo (estrutura de dados) para extrair o vértice mais próximo em O(log V). Com um array simples, a mesma lógica seria O(V²). A escolha da estrutura altera a complexidade do algoritmo. As duas coisas são inseparáveis.

Como decidir na prática: se você precisa de acesso direto por posição, arrays tendem a vencer. Se precisa inserir e remover muito no início ou no meio, listas ligadas podem evitar deslocamentos, embora paguem com pior localidade de cache. Se precisa sempre pegar o menor ou maior elemento, heap é mais adequado que ordenar tudo repetidamente. Se precisa responder "este elemento existe?" muitas vezes, uma tabela hash costuma ser melhor que uma busca linear. Estruturas diferentes tornam baratas operações diferentes.

Próximo passo

Se algoritmo e estrutura vivem juntos, precisamos de uma forma de falar das operações esperadas sem amarrar o aluno a uma implementação específica. É exatamente isso que o TAD faz: ele separa o contrato ("o que deve acontecer") da representação interna ("como acontece").

// 05 · e daí surge o tad — abstraindo a estrutura do algoritmo
Uma vez entendido que algoritmos precisam de estruturas, surge um problema prático: se eu mudar a estrutura interna (de array para lista ligada, por exemplo), preciso reescrever o algoritmo inteiro? A resposta, com um bom projeto de software, é não — e é exatamente aí que entra o conceito de Tipo Abstrato de Dado (TAD).
①
Algoritmo precisa de dados
Ex: BFS precisa de uma estrutura que suporte enqueue e dequeue
②
TAD define o contrato
Queue<T> com offer() e poll() — o quê, não o como
③
Implementação concreta
ArrayDeque, LinkedList — o como, invisível ao BFS
A progressão lógica deste módulo: entendemos o que é um algoritmo → entendemos que ele precisa de estruturas para operar → entendemos que precisamos de uma forma de especificar essas estruturas sem nos comprometer com uma implementação → chegamos ao TAD. Não é coincidência que o próximo tópico seja exatamente sobre isso.

// 01 · o paradoxo da caixa preta
definição — Liskov & Zilles (1974)
Um Tipo Abstrato de Dado (TAD) é um modelo matemático para tipos de dados, definido pelo seu comportamento (operações e axiomas) do ponto de vista de quem usa — não de quem implementa. O TAD especifica o quê uma estrutura faz, isolando completamente o como ela faz.
Ref: Liskov, B., Zilles, S. "Programming with Abstract Data Types." ACM SIGPLAN, 1974.
Analogia — o gerenciador de senhas: imagine um gerenciador de senhas moderno. Como usuário, você interage com comandos simples: salvar_senha(), buscar_senha(), gerar_senha_forte(). Você não precisa saber qual algoritmo de criptografia está rodando nos bastidores (AES-256? ChaCha20?), nem como os dados são persistidos internamente.

Se amanhã o desenvolvedor trocar a criptografia de AES para ChaCha20, ou mover o armazenamento de local para nuvem, o código que usa o gerenciador não quebra — porque a interface (o TAD) permanece a mesma. Isso é encapsulamento: o pulo do gato para o mercado de trabalho.
// 01.1 · tad, estrutura concreta e classe não são a mesma coisa
a confusão mais comum
O estudante costuma misturar três camadas: o TAD, a estrutura de dados concreta e a classe escrita em Java. Elas conversam, mas não são sinônimos. O TAD é a promessa pública; a estrutura concreta é a estratégia de armazenamento; a classe é uma implementação específica dessa estratégia numa linguagem.
CamadaPergunta que respondeExemploPor que importa
TADQuais operações existem e quais regras obedecem?Stack: push, pop, peekPermite raciocinar sem depender da implementação.
Estrutura concretaComo os dados ficam organizados na memória?Array dinâmico ou lista ligadaDetermina custos, limites e comportamento prático.
Classe JavaComo isso foi codificado nesta linguagem?ArrayDeque, LinkedList, ArrayStackExpõe a API real que o programa usa.
Exemplo de escolha: uma pilha usada para desfazer ações num editor de texto pode ser implementada com array dinâmico, porque push/pop no topo são rápidos e há boa localidade de memória. Uma fila de eventos com muitas remoções no início pode pedir outra estratégia, como buffer circular. O TAD diz o contrato; a implementação decide o custo.
// 02 · os dois pilares de todo TAD
PILAR 1 — DADOS
O estado interno — a coleção de valores que a estrutura mantém. Invisível para o usuário. No gerenciador de senhas: o cofre criptografado. Na pilha: o array interno e o ponteiro de topo.
PILAR 2 — OPERAÇÕES
As funções que o usuário pode chamar — a interface pública. Visível e estável. No gerenciador: salvar, buscar, gerar. Na pilha: push, pop, peek. São elas que formam o contrato.
O terceiro elemento: axiomas. Além de dados e operações, um TAD formal inclui axiomas — regras algébricas que as operações devem sempre satisfazer, independente de implementação. Ex: pop(push(s, x)) = s é um axioma da pilha. Ele é verdadeiro para array, lista ligada, ou qualquer outra implementação.
Ponte para estruturas lineares: depois que você entende o contrato, fica mais fácil comparar implementações. Uma pilha pode ser "a mesma pilha" para quem usa, mas custar diferente por dentro. O próximo bloco da plataforma começa justamente pela família mais direta de representações: arrays, listas, pilhas e filas. Elas são o primeiro laboratório para perceber que interface e custo não são a mesma coisa.

// 05 · implementação Java — Stack<T>
Java · Stack<T> implementando o TAD com array dinâmico
public class ArrayStack<T> implements Stack<T> {
    private Object[] data;     // detalhe interno — invisível ao usuário
    private int top = -1, capacity;

    public ArrayStack(int cap) { data = new Object[capacity = cap]; }

    public void push(T v) { if (++top == capacity) resize(); data[top] = v; }

    @SuppressWarnings("unchecked")
    public T pop() {
        if (isEmpty()) throw new EmptyStackException();
        T v = (T) data[top]; data[top--] = null; return v;
    }
    public boolean isEmpty() { return top == -1; }
    public int     size()    { return top + 1; }
    private void   resize()  { data = Arrays.copyOf(data, capacity *= 2); }
}

// 01 · o que mede
definição
A notação assintótica descreve como o tempo de execução (ou espaço) de um algoritmo cresce em função do tamanho da entrada n quando n tende ao infinito — ignorando constantes multiplicativas e termos de ordem menor.
Analogia: é como medir o consumo de um carro em km/l ignorando o tamanho do tanque. O que importa é a taxa de crescimento, não o valor absoluto. Um carro que faz 15 km/l sempre é mais eficiente que um que faz 8 km/l, independente do tanque. Da mesma forma, O(log n) sempre supera O(n) para entradas grandes o suficiente.
// 02 · as três notações
O(g(n))
LIMITE SUPERIOR
f(n) ≤ c·g(n) para todo n ≥ n₀. "No máximo cresce assim." Usado para o pior caso.
Ω(g(n))
LIMITE INFERIOR
f(n) ≥ c·g(n) para todo n ≥ n₀. "No mínimo cresce assim." Define o teto de qualquer algoritmo.
Θ(g(n))
LIMITE EXATO
f(n) é O(g) e Ω(g) ao mesmo tempo. "Cresce exatamente assim." O mais preciso dos três.
Atenção terminológica: na prática programadores frequentemente dizem "O(n log n)" quando tecnicamente querem dizer "Θ(n log n)". O CLRS distingue os três rigorosamente. Quando alguém diz "Merge Sort é O(n log n)", o correto seria Θ(n log n) — ele sempre custa exatamente esse tempo, não apenas "no máximo".

// 01 · o que a análise realmente mede

Analisar algoritmo é prever comportamento antes de rodar

Quando você pergunta "isso é rápido?", a resposta honesta é: depende do tamanho da entrada, da operação dominante e da estrutura de dados escolhida. A análise assintótica troca o cronômetro por uma lupa: em vez de medir uma máquina específica, ela descreve como o custo cresce quando n aumenta.

Por isso ela não substitui benchmark. Ela responde outra pergunta: se a entrada dobrar, o trabalho cresce pouco, cresce em linha reta, explode quadraticamente ou fica quase parado?

A receita mental

  1. Defina o que é n: quantidade de elementos, vértices, arestas, caracteres ou chamadas.
  2. Escolha a operação que domina o custo: comparação, troca, acesso, chamada recursiva ou visita.
  3. Conte quantas vezes ela acontece no pior caso relevante.
  4. Descarte constantes e termos menores: 3n² + 7n + 42 vira O(n²).
  5. Interprete: complexidade é uma pista de projeto, não um troféu isolado.
Melhor caso · Ω

Entrada mais favorável. Na busca linear, se o elemento está na primeira posição, há uma comparação: Ω(1). É útil para entender potencial, mas raramente basta para garantir qualidade.

Caso médio

Comportamento esperado sob uma distribuição de entradas. Busca linear costuma achar o item no meio: cerca de n/2 comparações, ainda O(n). Exige cuidado probabilístico.

Pior caso · O

O teto de custo. Se o item não existe, a busca linear olha tudo: n comparações. É a visão preferida quando o sistema precisa prometer desempenho previsível.

// 02 · comparando escolhas reais
Cartões comparativos: escolha pelo contexto do problema
Busca linear Funciona em dados desordenados e é simples. Boa para listas pequenas, uma única consulta ou quando ordenar custaria mais que procurar.
Busca binária Exige dados ordenados e acesso por índice. Em arrays, corta o espaço pela metade a cada passo: O(log n). Em lista ligada, perde força porque chegar ao meio custa caro.
Tabela hash Troca ordenação por acesso por chave. No caso médio, busca é O(1); no pior, colisões ruins podem degradar. É ótima para dicionários, caches e cadastros.
Árvore balanceada Mantém ordem e busca previsível: O(log n). Serve quando você precisa inserir, remover e ainda percorrer em ordem sem reordenar tudo.
💡
Leitura de projeto

Não existe "melhor algoritmo" fora do contexto. Se você consulta muito e muda pouco, ordenar e usar busca binária pode valer. Se consulta por chave o tempo todo, hash costuma vencer. Se precisa manter ordem enquanto insere, árvore balanceada entra em cena.

Checklist de leitura: use como alertas de projeto
Confundir rápido com escalável Um algoritmo O(n²) pode parecer ótimo em 20 itens e desabar em 200 mil. Assintótica revela essa curva antes do susto.
Ignorar espaço Merge Sort é previsível, mas usa memória extra. Quick Sort costuma ser econômico em memória, mas pode ter pior caso ruim se o pivô for escolhido mal.
Esquecer a estrutura de dados O mesmo algoritmo muda de custo quando troca array por lista ligada. Busca binária precisa saltar para o meio; lista ligada não sabe fazer isso barato.
Usar Big-O como ranking absoluto O(log n) não vence sempre se a constante, o cache, a entrada e o custo de preparar os dados forem desfavoráveis. A análise orienta; o contexto decide.

// 01 · memória contígua
definição
Um array armazena elementos em posições de memória contíguas. O acesso a qualquer elemento é O(1) pelo cálculo: addr(i) = base + i × sizeof(T)
Analogia: caixas postais numeradas num prédio. Para acessar a caixa 47, você vai diretamente — não precisa abrir as anteriores. Custo sempre O(1). Mas inserir uma nova caixa no meio exige mover todas as posteriores.
Por que arrays foram criados? O problema original era representar uma coleção homogênea de valores sem criar uma variável para cada item. Em computação numérica, tabelas, matrizes, buffers e memória de baixo nível, era preciso dizer: "guarde muitos elementos do mesmo tipo em sequência e me deixe acessar qualquer posição rapidamente". O array resolveu isso de forma excelente: transforma índice em endereço por aritmética simples.
Leitura guiada: origem, acesso, ganho e limite
Política de acesso: acesso aleatório por índice. Você pede arr[i] e a máquina calcula diretamente onde o elemento está.
Como o dado é alcançado: por endereço base mais deslocamento: base + i * tamanho. Não há nós, links ou busca estrutural.
O que resolveu bem: leitura rápida, iteração cache-friendly, matrizes, vetores, ordenação, busca binária em dados ordenados e representação compacta.
O que não resolveu: crescimento flexível e inserção no meio. Para manter continuidade, elementos precisam ser deslocados.
Leitura guiada: decisão de uso e trade-offs
Use array quando: o tamanho é conhecido ou cresce pouco, o acesso por índice é frequente e você percorre os dados muitas vezes. É o caso de vetores numéricos, tabelas compactas, buffers e algoritmos de ordenação.
Evite array puro quando: você precisa inserir/remover no meio com frequência. Cada deslocamento pode custar O(n), porque os elementos precisam continuar contíguos.
ArrayList resolve parte do problema: cresce dinamicamente e mantém acesso O(1), mas ainda paga caro para inserir no meio. Ele melhora conveniência, não muda a natureza contígua.
Lista ligada resolve outro problema: inserir/remover depois de um nó conhecido pode ser O(1), mas buscar o nó custa O(n) e a localidade de cache é pior. Não existe almoço grátis.

🔬 Cache Locality — por que arrays são mais rápidos que listas na prática
A complexidade teórica diz que iterar sobre um array e sobre uma lista ligada são ambos O(n). Na prática, um array pode ser 3–10× mais rápido. O motivo é a hierarquia de memória do processador — e é aqui que O(n) == O(n) deixa de ser verdade fora do papel.
ARRAY — CACHE FRIENDLY
Elementos contíguos na memória. A CPU carrega uma linha de cache (~64 bytes = 16 ints) de uma vez. Os próximos 15 acessos atingem o cache L1. Cache hit ratio ≈ 99%.
LISTA LIGADA — CACHE HOSTILE
Cada nó está num endereço de heap aleatório. Cada acesso ao próximo nó pode ser um cache miss — busca na RAM (~100ns vs ~1ns no L1). Cache miss ratio pode chegar a 90%.

// 01 · pilha LIFO
Last In, First Out
Uma pilha restringe inserção e remoção a uma única extremidade chamada topo. O último elemento inserido é sempre o primeiro a sair.
Analogia: pilha de pratos. Você sempre coloca e retira do topo. A call stack do Java funciona exatamente assim — cada chamada empilha um frame, cada retorno o desempilha. StackOverflowError ocorre quando a pilha excede o limite de frames.
Leitura guiada: problema, política, acesso e uso
Problema que motivou: controlar processos reversíveis: chamadas de função, desfazer ações, parsing de parênteses, backtracking e navegação por histórico.
Política de acesso: acesso restrito ao topo. Não se percorre a pilha para escolher qualquer elemento; a disciplina é justamente remover o mais recente.
Como o dado é acessado: por ponteiro/índice de topo. Em array, top aponta para a última posição ocupada; em lista, head é o topo.
Quando usar: quando o último evento precisa ser resolvido primeiro. Se a ordem correta é "primeiro que chegou, primeiro atendido", use fila.
// 02 · fila FIFO
First In, First Out
Uma fila insere no fim (enqueue) e remove do início (dequeue). O primeiro a entrar é o primeiro a sair.
Analogia: fila de supermercado. Quem chega primeiro é atendido primeiro. BFS usa uma fila exatamente por esse motivo — explora todos os vizinhos a distância 1 antes de ir para distância 2, processando nós na ordem de descoberta.
Leitura guiada: problema, política, acesso e limite
Problema que motivou: organizar atendimento justo e processamento por ordem de chegada: tarefas, pacotes de rede, eventos de interface e níveis em BFS.
Política de acesso: insere atrás, remove na frente. A estrutura impede "furar fila" porque isso quebraria a semântica FIFO.
Como o dado é acessado: por dois marcadores: front para remover e rear para inserir. Em array eficiente, usa-se buffer circular.
Quando evitar: se você precisa buscar o maior, menor ou mais urgente, fila simples não basta. A próxima variação natural é fila de prioridade, normalmente baseada em heap.

// 01 · nós e ponteiros
definição
Uma lista ligada é uma sequência de nós, onde cada nó contém um valor e um ponteiro para o próximo nó. Os nós podem estar em posições de memória não-contíguas — eles se encontram pelos ponteiros.
Analogia: caça ao tesouro. Cada pista (nó) diz onde encontrar a próxima. Para chegar à pista 47, você tem que seguir toda a cadeia a partir do início — não há como ir diretamente: O(n). Em compensação, inserir uma nova pista no meio exige apenas atualizar dois ponteiros — O(1) se você já tem o nó anterior.
Por que listas ligadas foram criadas? Arrays exigem blocos contíguos e sofrem para inserir/remover no meio. Em sistemas onde a memória pode estar fragmentada ou onde o tamanho da coleção muda muito, a lista ligada oferece outra ideia: cada elemento carrega o endereço do próximo. Ela resolveu bem crescimento flexível e edição local, mas pagou com perda de acesso direto.
Leitura guiada: origem, acesso, ganho e limite
Política de acesso: acesso sequencial por nós. Para chegar ao elemento i, você começa em head e segue next i vezes.
Como o dado é acessado: por referência, não por índice real. O índice é uma contagem durante a travessia; ele não vira endereço direto como no array.
O que resolveu bem: inserção/remoção no início, filas com ponteiros, estruturas encadeadas, listas intrusivas em sistemas e histórico com avanço/retorno.
O que não resolveu: busca aleatória. Pedir "me dê o 47º" custa percorrer 46 links antes. Além disso, cada nó tem overhead de ponteiro e pior cache.

🔬 Por que a Lista Ligada perde para o Array mesmo sendo O(n) == O(n)
Percorrer 10 milhões de nós numa lista ligada pode ser 5–8x mais lento que percorrer um array de mesmo tamanho. A razão é que cada nó da lista está num endereço de heap alocado aleatoriamente pelo new. O hardware prefetcher da CPU não consegue prever onde está o próximo nó — cada acesso a node.next pode forçar uma busca na RAM.

Árvore de Busca Binária — BST
teoriaestruturaimplementaçãocomplexidade
// 01 · invariante
invariante da BST
Para todo nó N: todos os valores na subárvore esquerda são menores que N, e todos na subárvore direita são maiores. Essa propriedade vale recursivamente para cada nó da árvore toda.
Analogia: a BST é a busca binária em forma de árvore. Cada nó "dobra o papel" e descarta metade do espaço restante. A invariante garante que a estrutura já está sempre "pré-ordenada", então cada busca aproveita isso para descer O(log n) níveis — sem precisar organizar nada antes.
Leitura guiada: problema, política, acesso e consequência
Problema que motivou: manter uma coleção ordenável com inserções e buscas mais rápidas que varrer uma lista inteira.
Política de acesso: comparação hierárquica. Em cada nó, decide-se ir para a esquerda ou direita; não existe acesso por índice.
Como o dado é acessado: por caminho da raiz até o nó. O custo depende da altura da árvore, não diretamente da quantidade de elementos.
Resolveu? sim, quando a árvore está razoavelmente balanceada. Quando os dados chegam ordenados, ela degenera e perde a vantagem.
Degeneração: inserindo elementos em ordem crescente (1, 2, 3, 4…), a BST vira uma lista ligada com altura n e O(n) por operação. AVL e Red-Black resolvem isso garantindo altura O(log n) em qualquer caso.

teoriabalanceamentoimplementaçãocomplexidade
// 01 · invariante de balanceamento
fator de balanceamento BF
Para todo nó N: BF(N) = altura(esq) − altura(dir) ∈ {−1, 0, +1}. Toda inserção que viola essa invariante dispara rotações para restaurar o equilíbrio — em O(1) rotações por inserção.
Analogia: um mobile de crianças. Cada braço deve estar equilibrado — se você pendura um peso novo em um lado, um contrapeso automático aparece do outro. As rotações AVL são esse mecanismo: ao detectar BF > 1 ou BF < −1, a árvore redistribui nós para restaurar o equilíbrio, garantindo altura O(log n) para sempre.
Leitura guiada: motivação, acesso, garantia e custo
Problema que motivou: a BST simples depende da ordem de inserção. AVL foi criada para impedir que uma árvore de busca vire lista ligada.
Política de acesso: igual à BST: comparação a partir da raiz. A diferença é que a estrutura se reorganiza para manter caminhos curtos.
Como o dado é acessado: por caminho de comparações, com altura garantida O(log n). Rotações preservam a ordem em percurso in-order.
Resolveu? sim para busca previsível. O custo é mais manutenção em inserções/remoções, pois a árvore precisa recalcular alturas e rotacionar.

Heap
teoriaestruturaimplementaçãocomplexidade
// 01 · propriedade heap e representação em array
max-heap
Árvore binária completa onde todo nó é ≥ seus filhos. O maior elemento fica sempre na raiz — acessível em O(1). Armazenado em array plano: pai de i em ⌊(i−1)/2⌋, filhos de i em 2i+1 e 2i+2.
Truque elegante: a árvore é completa (sem buracos), então o mapeamento para array é perfeito. Não há ponteiros — a posição no array é a estrutura. É como um mapa de assentos num teatro: saber o número do seu assento já diz exatamente onde sentar.
Leitura guiada: problema, prioridade, acesso e aplicação
Problema que motivou: manter sempre disponível o maior ou menor elemento sem ordenar toda a coleção a cada mudança.
Política de acesso: acesso prioritário à raiz. O heap não promete achar qualquer valor rápido; ele promete achar o extremo rápido.
Como o dado é acessado: por índices que simulam pai e filhos. A raiz é 0; filhos de i são 2i+1 e 2i+2.
Resolveu? sim para filas de prioridade, escalonadores, Dijkstra e Heap Sort. Não substitui BST quando você precisa buscar valores arbitrários.

Tabelas Hash
teoriaestruturaimplementaçãocomplexidade
// 01 · o que é e por que importa
definição
Uma tabela hash é uma estrutura de dados que mapeia chaves para valores usando uma função de hash — uma função que converte a chave em um índice de array. O objetivo é atingir O(1) para inserção, busca e remoção no caso médio.
Analogia — vestiário de clube: você chega com seu casaco (valor) e recebe um número de cabide (hash). Para recuperar o casaco, você dá o número — acesso direto, O(1). O atendente (função de hash) decide qual número dar baseado no seu nome. O problema: dois sócios com o mesmo número de cabide (colisão) — e isso acontece inevitavelmente pelo Princípio da Casa dos Pombos.
Leitura guiada: chave, acesso, colisão e limite
Problema que motivou: procurar por chave muito rapidamente: nome de usuário, CPF, token de sessão, palavra em dicionário, id de produto.
Política de acesso: acesso por chave. Você não pergunta "posição 7"; pergunta "valor associado à chave X".
Como o dado é acessado: a chave passa por hashCode(), vira índice de array e, se houver colisão, a estrutura procura dentro do balde.
Resolveu? sim no caso médio. O preço é aceitar colisões, redimensionamento e ausência de ordem natural entre chaves.
Possivelmente a estrutura mais cobrada em entrevistas técnicas. Saber explicar como funciona uma função de hash, por que colisões são inevitáveis, e como tratá-las é requisito absoluto para posições de engenharia de software. O Java HashMap e o Python dict são tabelas hash.
// 02 · a função de hash — requisitos
DETERMINÍSTICA
Mesma chave → sempre mesmo índice. Sem aleatoriedade.
UNIFORME
Distribui as chaves uniformemente pelo array. Minimiza colisões.
EFICIENTE
O(1) para calcular. Uma hash lenta anula o ganho da estrutura.
Java · funções de hash comuns
// Hash simples por módulo (inteiros)
int hash(int key, int tableSize) {
    return key % tableSize; // índice em [0, tableSize-1]
}

// Hash polinomial para strings (djb2 simplificado)
int hashString(String s, int tableSize) {
    int h = 0;
    for (char c : s.toCharArray())
        h = h * 31 + c; // 31 é primo — boa distribuição
    return Math.abs(h) % tableSize;
}

// 03 · colisões — tratamento
ENCADEAMENTO (CHAINING)
Cada posição do array aponta para uma lista ligada de entradas que colidem. Inserção sempre O(1). Busca O(1) no caso médio, O(n) no pior (todos na mesma lista).
índice 0 → [A] → [E] → null
índice 1 → [B] → null
índice 2 → [C] → [F] → null
ENDEREÇAMENTO ABERTO
Todas as entradas ficam no array. Em caso de colisão, sonda posições alternativas. Linear probing: tenta i+1, i+2… Double hashing: usa segunda função hash.
Melhor localidade de cache que chaining. Mais sensível ao fator de carga.
Fator de carga α = n / m (n = entradas, m = tamanho da tabela). O desempenho degrada quando α > 0.75. O Java HashMap usa chaining e dobra a tabela quando α excede 0.75, redistribuindo todas as entradas — O(n) amortizado.

Isso levou ao uso de hash randomization (seed aleatório por processo) em praticamente todas as implementações modernas. Em Java: String.hashCode() foi complementado com perturbação aleatória no HashMap; em Python: PYTHONHASHSEED.

Algoritmos O(n²) — os algoritmos base
teoriacomparaçãoimplementaçãoO(n²)
// 01 · por que estudar algoritmos lentos?
Antes de entender por que Merge Sort e Quick Sort são brilhantes, é preciso entender o problema que eles resolvem. Os algoritmos O(n²) mostram o custo de abordagens ingênuas — e, ao estudá-los, você desenvolve a intuição para reconhecer desperdício computacional. Além disso, para arrays pequenos (< 20 elementos), Insertion Sort frequentemente supera Merge Sort na prática por ter constante menor e melhor localidade de cache. Saber quando usar o "lento" é tão importante quanto saber usar o rápido.
// 02 · bubble sort — o mais intuitivo
estratégia
Em cada passagem, compara pares adjacentes e os troca se estiverem fora de ordem. O maior elemento "borbulha" para o final a cada passagem. Após k passagens, os k maiores elementos estão em posição definitiva.
Analogia: bolhas de ar subindo na água — os elementos mais "pesados" (maiores) afundam gradualmente para o final. A cada ronda, uma bolha chega ao topo. É visualmente elegante, mas cada ronda percorre o array inteiro: O(n²) no total.
Java · Bubble Sort
public static void bubbleSort(int[] arr) {
    int n = arr.length;
    for (int i = 0; i < n - 1; i++) {
        boolean swapped = false;
        for (int j = 0; j < n - i - 1; j++) {
            if (arr[j] > arr[j + 1]) {
                int tmp = arr[j]; arr[j] = arr[j+1]; arr[j+1] = tmp;
                swapped = true;
            }
        }
        if (!swapped) break; // otimização: array já ordenado → O(n)
    }
} // Pior/médio: O(n²) · Melhor: O(n) · Estável: sim · Espaço: O(1)
// 03 · selection sort — o mais simples de entender
estratégia
Encontra o menor elemento do subarray não-ordenado e o coloca na posição correta. Repete para o restante. Sempre faz exatamente n(n-1)/2 comparações — sem atalhos, mesmo para arrays já ordenados.
Analogia: escolher o menor número de uma mão de cartas, colocá-lo na mesa, repetir. Simples e previsível — mas você percorre as cartas restantes cada vez do início. Curiosidade: Selection Sort faz o mínimo de trocas entre os algoritmos O(n²) — no máximo n-1 trocas. Útil quando trocas são custosas (escrita em memória flash, por exemplo).
Java · Selection Sort
public static void selectionSort(int[] arr) {
    int n = arr.length;
    for (int i = 0; i < n - 1; i++) {
        int minIdx = i;
        for (int j = i + 1; j < n; j++)
            if (arr[j] < arr[minIdx]) minIdx = j;
        int tmp = arr[i]; arr[i] = arr[minIdx]; arr[minIdx] = tmp;
    }
} // Sempre O(n²) · n-1 trocas (mínimo) · Não-estável · Espaço: O(1)
// 04 · insertion sort — o mais prático
estratégia
Mantém um subarray esquerdo sempre ordenado. Para cada novo elemento, encontra sua posição correta no subarray esquerdo deslocando os maiores. Análogo a organizar cartas na mão.
Por que Insertion Sort ainda é relevante: para arrays pequenos ou quase ordenados, é frequentemente o mais rápido na prática. Timsort — o algoritmo usado internamente por Java (Arrays.sort para objetos) e Python — usa Insertion Sort para subarrays de tamanho < 64.
Java · Insertion Sort
public static void insertionSort(int[] arr) {
    for (int i = 1; i < arr.length; i++) {
        int key = arr[i], j = i - 1;
        while (j >= 0 && arr[j] > key) {
            arr[j + 1] = arr[j]; // desloca para abrir espaço
            j--;
        }
        arr[j + 1] = key; // insere na posição correta
    }
} // Melhor: O(n) · Médio/Pior: O(n²) · Estável: sim · Online: sim

Merge Sort
divisão e conquistaestávelimplementação
// estratégia
divide para conquistar
Divide recursivamente o array ao meio até ter subarrays de tamanho 1 (trivialmente ordenados), depois intercala (merge) os pares ordenados, produzindo sequências maiores já ordenadas. T(n) = 2T(n/2) + O(n) → Caso 2 do Teorema Mestre → O(n log n).
Analogia: dois baralhos já ordenados que você precisa combinar. Você compara as cartas do topo dos dois montes e sempre pega a menor. Merge Sort primeiro divide até montes de 1 carta (já ordenados), depois reconstrói fazendo merges. Cada nível de merge custa O(n), há O(log n) níveis → O(n log n) total.
// implementação Java
Java · Merge Sort recursivo
public static void mergeSort(int[] arr, int lo, int hi) {
    if (lo >= hi) return;
    int mid = lo + (hi - lo) / 2;
    mergeSort(arr, lo, mid);
    mergeSort(arr, mid + 1, hi);
    merge(arr, lo, mid, hi);
}
private static void merge(int[] arr, int lo, int mid, int hi) {
    int[] tmp = Arrays.copyOfRange(arr, lo, hi + 1);
    int i = 0, j = mid - lo + 1, k = lo;
    while (i <= mid - lo && j < tmp.length) {
        if (tmp[i] <= tmp[j]) arr[k++] = tmp[i++];
        else                  arr[k++] = tmp[j++];
    }
    while (i <= mid - lo) arr[k++] = tmp[i++];
    while (j < tmp.length)  arr[k++] = tmp[j++];
}

Quick Sort
divisão e conquistain-placeimplementação
// estratégia
particionar em torno de um pivô
Escolhe um elemento como pivô e reorganiza o array para que todos os menores fiquem à esquerda e maiores à direita. O pivô já está na posição final após a partição. Aplica recursivamente em cada lado.
Pior caso O(n²): ocorre quando o pivô é sempre o menor ou maior elemento — como ao ordenar um array já ordenado com pivô = primeiro elemento. Cada partição divide 1 e (n-1): T(n) = T(n-1) + O(n) = O(n²). Pivô aleatório ou mediana de 3 reduz esse risco drasticamente na prática.
// implementação Java
Java · Quick Sort — partição de Lomuto
public static void quickSort(int[] arr, int lo, int hi) {
    if (lo >= hi) return;
    int p = partition(arr, lo, hi);
    quickSort(arr, lo, p - 1);
    quickSort(arr, p + 1, hi);
}
private static int partition(int[] arr, int lo, int hi) {
    int pivot = arr[hi]; int i = lo - 1;
    for (int j = lo; j < hi; j++) {
        if (arr[j] <= pivot) {
            i++;
            int tmp = arr[i]; arr[i] = arr[j]; arr[j] = tmp;
        }
    }
    int tmp = arr[i+1]; arr[i+1] = arr[hi]; arr[hi] = tmp;
    return i + 1; // pivô na posição final
}
grafos · 01
Grafos — BFS e DFS
teoriatravessiaimplementaçãocomplexidade
// 01 · teoria
G = (V, E)
Um grafo é um conjunto de vértices V e arestas E. Pode ser dirigido, não-dirigido, ponderado ou não. BFS usa uma fila — expande por nível, garante caminho mínimo em arestas. DFS usa pilha/recursão — vai fundo antes de voltar, base para ciclos e ordenação topológica. Ambos: O(V + E).
Analogia BFS vs DFS: explorar um labirinto. BFS é uma onda de água espalhando-se radialmente — todos os caminhos a distância 1, depois 2, depois 3. DFS é um espeleólogo: vai fundo numa galeria até o fim, depois volta e tenta outra. BFS encontra o caminho mais curto (em número de arestas). DFS encontra algum caminho, mas não necessariamente o menor.
Leitura guiada: relação, adjacência, representação e algoritmo
Problema que motivou: representar relações que não cabem em sequência linear: rotas, redes, dependências, estados, conexões sociais e links.
Política de acesso: acesso por adjacência. A pergunta central é: "quais vértices são vizinhos deste vértice?".
Como o dado é acessado: por lista de adjacência, matriz de adjacência ou mapa de vizinhos. Lista economiza memória em grafos esparsos; matriz consulta aresta em O(1), mas custa O(V²).

public List<Integer> bfs(List<List<Integer>> adj, int start) {
    boolean[] visited = new boolean[adj.size()];
    List<Integer> order = new ArrayList<>();
    Queue<Integer> queue = new LinkedList<>();
    visited[start] = true; queue.offer(start);
    while (!queue.isEmpty()) {
        int v = queue.poll(); order.add(v);
        for (int nb : adj.get(v))
            if (!visited[nb]) { visited[nb] = true; queue.offer(nb); }
    }
    return order; // O(V + E)
}

// 01 · invariante
invariante de Dijkstra
Mantém um conjunto de vértices "finalizados" com distâncias mínimas já conhecidas. A cada passo, extrai o vértice não-finalizado de menor distância estimada e relaxa suas arestas — atualiza distâncias dos vizinhos se encontrou caminho mais curto.
Analogia: ondas de rádio espalhando-se de uma torre. A onda chega primeiro nos pontos mais próximos. Dijkstra processa vértices em ordem crescente de distância — quando um vértice é processado, seu caminho mínimo já é definitivo. O "relaxamento" é como atualizar o GPS ao descobrir uma rota mais curta.
Limitação crítica: Dijkstra não funciona com arestas de peso negativo. A invariante assume que ao finalizar um vértice, nenhum caminho futuro pode chegar nele mais barato. Com pesos negativos, uma aresta negativa via vértice já finalizado pode criar caminho mais curto — violando a invariante. Use Bellman-Ford para grafos com pesos negativos.

public int[] dijkstra(List<int[][]> adj, int src, int V) {
    int[] dist = new int[V]; Arrays.fill(dist, Integer.MAX_VALUE);
    dist[src] = 0;
    PriorityQueue<int[]> pq = new PriorityQueue<>(Comparator.comparingInt(a -> a[0]));
    pq.offer(new int[]{0, src});
    while (!pq.isEmpty()) {
        int[] cur = pq.poll(); int d = cur[0], u = cur[1];
        if (d > dist[u]) continue; // entrada obsoleta
        for (int[] edge : adj.get(u)) {
            int v = edge[0], w = edge[1];
            if (dist[u] + w < dist[v]) {
                dist[v] = dist[u] + w; // relaxamento
                pq.offer(new int[]{dist[v], v});
            }
        }
    }
    return dist; // O((V+E) log V)
}

// 01 · estrutura geral
divide → conquista → combina
Divide o problema de tamanho n em a subproblemas de tamanho n/b (independentes). Resolve cada um recursivamente. Combina as soluções parciais. A recorrência T(n) = a·T(n/b) + f(n) é resolvível pelo Teorema Mestre.
Analogia: organizar uma eleição num país continental. Divide em estados, depois municípios, depois seções eleitorais. Cada seção conta seus votos independentemente, os resultados sobem hierarquicamente até o total nacional. Os subproblemas não se importam uns com os outros — a seção de Manaus não precisa saber o resultado de Recife para contar seus votos. Essa independência é a marca do D&C.
Quando D&C falha: se o mesmo subproblema aparecer múltiplas vezes na recursão (como Fibonacci ingênuo), D&C puro recomputa exponencialmente. Nesses casos a ferramenta correta é Programação Dinâmica.

public static long fastPow(long base, int exp) {
    if (exp == 0) return 1;
    long half = fastPow(base, exp / 2); // DIVIDE
    if (exp % 2 == 0) return half * half;          // COMBINA par
    else              return half * half * base;     // COMBINA ímpar
}

// 01 · as duas condições necessárias
quando usar PD
Um problema admite PD quando tem subestrutura ótima (a solução ótima do problema contém soluções ótimas dos subproblemas) e subproblemas sobrepostos (os mesmos subproblemas aparecem repetidamente na recursão ingênua). PD resolve cada um uma única vez e armazena em tabela (bottom-up) ou cache (top-down com memoização).
Analogia: calcular Fibonacci sem PD é como uma empresa onde cada funcionário que precisa de F(8) contrata dois assistentes para F(7) e F(6), que por sua vez contratam dois cada... A empresa cresce exponencialmente. Com PD, você cola um post-it na parede com cada resposta calculada. Qualquer um que precisar de F(8) lê o post-it — não refaz o cálculo. O(2ⁿ) vira O(n).
Distinção crítica com D&C: em D&C os subproblemas são independentes (metade esq e dir do array). Em PD os subproblemas se sobrepõem — F(5) é necessário para F(6) e para F(7). Sem memoização, a recursão recomputa F(5) um número exponencial de vezes. A sobreposição é o sinal de que PD é a ferramenta correta.

public static int knapsack(int[] weights, int[] values, int W) {
    int n = weights.length;
    int[][] dp = new int[n + 1][W + 1];
    for (int i = 1; i <= n; i++) {
        for (int w = 0; w <= W; w++) {
            dp[i][w] = dp[i - 1][w]; // não incluir
            if (weights[i-1] <= w) {
                int with = values[i-1] + dp[i-1][w-weights[i-1]];
                dp[i][w] = Math.max(dp[i][w], with);
            }
        }
    }
    return dp[n][W]; // O(n×W) tempo e espaço — pseudo-polinomial
}

// 01 · o que é e quando funciona
propriedade gulosa
Um algoritmo guloso faz, a cada passo, a escolha localmente ótima, sem reconsiderar decisões passadas. Para ser correto, o problema deve ter a propriedade gulosa: a escolha local ótima leva à solução globalmente ótima. Provar isso formalmente geralmente usa um exchange argument: mostrar que trocar a escolha gulosa por qualquer outra nunca melhora a solução.
Analogia: um turista com roteiro de cidades. Estratégia gulosa: ir sempre para a cidade mais próxima não-visitada. Para o Problema do Troco com moedas canônicas {1, 5, 10, 25¢}, o guloso funciona e é ótimo. Para o TSP (Problema do Caixeiro-Viajante), o guloso pode chegar a soluções 25% piores que o ótimo. A diferença está na estrutura matemática do problema.
Contraexemplo concreto: moedas {1, 3, 4} e troco = 6. Guloso escolhe 4 (maior ≤ 6), depois 1+1 → 3 moedas. PD encontra 3+3 → 2 moedas. O sistema não-canônico quebra a propriedade gulosa. Antes de usar guloso, pergunte: consigo provar que a escolha local não fecha portas para soluções melhores futuras?

KRUSKAL — MST
Ordena arestas por peso crescente, adiciona cada uma se não criar ciclo. Correto pela cut property: a aresta de menor peso que conecta dois componentes distintos sempre pertence a alguma MST.
HUFFMAN — COMPRESSÃO
Une sempre os dois nós de menor frequência. Correto por exchange argument: trocar a escolha gulosa nunca reduz o custo total de codificação.
DIJKSTRA
Finaliza sempre o vértice de menor distância. Correto porque com pesos positivos, ao finalizar um vértice nenhum caminho futuro pode chegar nele mais barato (desigualdade do triângulo).
INTERVAL SCHEDULING
Escolhe sempre o intervalo com menor tempo de término. Correto por exchange: substituir o intervalo guloso por qualquer outro nunca aumenta o número de intervalos selecionáveis.
// 04 · implementação Java — Interval Scheduling
Java · Interval Scheduling Maximization
public static int maxActivities(int[][] intervals) {
    Arrays.sort(intervals, (a, b) -> a[1] - b[1]); // ordena por fim
    int count = 1, lastEnd = intervals[0][1];
    for (int i = 1; i < intervals.length; i++) {
        if (intervals[i][0] >= lastEnd) { // não sobrepõe
            count++; lastEnd = intervals[i][1];
        }
    }
    return count; // O(n log n) — dominado pela ordenação
}

// como fim(i) ≤ fim(j), trocar j por i é sempre válido — logo guloso é ótimo.
